# 4.3 · Several Agents Together: Subagent Audit & Role Handoffs (10 นาที)

**สิ่งที่จะฝึก:** ให้หลาย Custom Agents ทำงานร่วมกันทั้ง 2 รูปแบบจากสไลด์ 12–14:
1. **Subagent (สไลด์ 13):** ให้ Role Agent ของคุณเรียก `release-auditor` ไปรันตรวจผลงานใน **Context แยกต่างหาก** แล้วส่งกลับมาเฉพาะผลสรุป
2. **Handoffs / การส่งไม้ต่อข้ามสายงาน BA → Dev → QA → Auditor (สไลด์ 12 & สไลด์ 7):** ส่งต่อบทสนทนาเดียวกันให้บทบาทถัดไปทำงานต่อโดยมีคนตรวจคั่นกลาง

### ทำไมไม่เรียก Skill ถัดไปใน Agent ตัวเดิม?

- **ทำได้** ถ้าต้องการเพียงเปลี่ยนวิธีทำงาน เช่น จากเขียน Spec ไปออกแบบ Test Matrix โดยยังใช้บทบาทและเครื่องมือเดิม
- แต่ตอนให้ **ผู้สร้าง → ผู้ตรวจ** เราต้องการให้ผู้ตรวจใช้โปรไฟล์ `read`, `search` แทนโปรไฟล์ที่มี `edit` การเปลี่ยน Skill อย่างเดียวไม่ได้เปลี่ยน `tools:`; ใช้ `release-auditor` เพื่อระบุบทบาทและเครื่องมือของผู้ตรวจที่เตรียมไว้ แล้วตรวจผลจริงตามข้อ 4.4
- **Subagent** เพิ่ม Context แยกสำหรับงานย่อย ไม่ใช่ความสามารถพิเศษที่ต้องเป็น Custom Agent เท่านั้น การใช้ชื่อ `release-auditor` ทำให้เรียกโปรไฟล์ผู้ตรวจเดิมซ้ำได้ ส่วน **Handoff** เปลี่ยนผู้รับผิดชอบในแชตเดิมเพื่อให้คนตรวจคั่นกลาง
- BA → Dev → QA ในแล็บนี้ยังมี `tools:` เท่ากัน จึงเป็นประโยชน์ด้านการเลือกหน้าที่ / เส้นทางส่งต่อ ไม่ใช่ข้อพิสูจน์ว่าทุกขั้นต้องมี Agent ใหม่

## 1. ส่วนที่ 1 · เรียก `release-auditor` เป็น Subagent มาตรวจผลงาน (5 นาที · สไลด์ 13)

จากสไลด์ 13 (*Subagents: A worker with its own context*):
เมื่อ Role Agent ของคุณ (`ba-analyst`, `qa-inspector` หรือ `dev-builder`) ทำงานเสร็จ เราสามารถให้ Agent เรียก **`release-auditor`** เป็น **Subagent** แทนการสลับ Agent เอง โดยให้ Subagent อ่านนโยบาย `docs/policies/finance-and-sla-policy.md` และเกณฑ์ใน Skill `release-gate-audit` ใน Context แยก แล้วส่งตารางผลตรวจกลับมา

1. เปิดไฟล์ Role Agent ของคุณใน `.github/agents/` (`ba-analyst.agent.md`, `qa-inspector.agent.md` หรือ `dev-builder.agent.md`)
2. เพิ่ม **`'agent'`** เข้าไปในรายการ `tools:` และเพิ่มบรรทัด **`agents: ['release-auditor']`** (สำหรับจำกัดรายชื่อ Subagent ใน Local harness ตามสไลด์ 13):
   ```yaml
   tools: ['read', 'search', 'edit', 'agent']
   agents: ['release-auditor']
   ```
   *(บันทึกไฟล์หลังแก้เสร็จ)*
3. เปิด **New Chat** → เลือก Role Agent ของคุณ (`ba-analyst`, `qa-inspector` หรือ `dev-builder`) แล้วส่งคำขอให้เรียก `release-auditor` เป็น Subagent มาตรวจผลงานจากข้อ 4.2:

   - **สำหรับสาย BA (`ba-analyst`):**
     ```text
     ช่วยเรียก subagent release-auditor มาตรวจสอบไฟล์ Spec ที่อยู่ในโฟลเดอร์ outputs/ba/ เทียบกับนโยบายใน docs/policies/finance-and-sla-policy.md แล้วสรุปผลการตรวจให้ฉันหน่อย
     ```
   - **สำหรับสาย QA (`qa-inspector`):**
     ```text
     ช่วยเรียก subagent release-auditor มาตรวจสอบไฟล์ Test Cases ที่อยู่ในโฟลเดอร์ outputs/qa/ เทียบกับนโยบายใน docs/policies/finance-and-sla-policy.md แล้วสรุปผลการตรวจให้ฉันหน่อย
     ```
   - **สำหรับสาย Dev (`dev-builder`):**
     ```text
     ช่วยเรียก subagent release-auditor มาตรวจสอบโค้ดในไฟล์ ui/preview.html เทียบกับนโยบายใน docs/policies/finance-and-sla-policy.md แล้วสรุปผลการตรวจให้ฉันหน่อย
     ```

**สังเกตสิ่งที่เกิดขึ้น (เทียบกับสไลด์ 13 & 14):**
- Role Agent ของคุณยังเป็นหัวหน้างาน (Coordinator) อยู่เหมือนเดิม แต่เกิดการเรียก Subagent (`task` ใน Copilot harness หรือ `runSubagent` ใน Local harness)
- `release-auditor` อ่านไฟล์นโยบายและ Checklist ใน **Context แยกของ Subagent** แล้วส่งกลับมาเฉพาะผลสรุป แชตหลักจึงไม่ต้องเก็บรายละเอียดการตรวจทั้งหมด
- เปิดรายละเอียด Subagent เพื่อยืนยันว่าเรียก **`release-auditor` จริง** และตรวจเครื่องมือของตัวลูก ไม่ใช่อนุมานจากชื่อในข้อความสรุป หากตรวจไม่ได้ให้บันทึกข้อจำกัด; อย่าสรุปว่า Context แยกแปลว่าข้อจำกัดเครื่องมือถูกบังคับแล้ว

## 2. ส่วนที่ 2 · ส่งต่องานข้ามสายงาน `BA → Dev → QA → Auditor` (5 นาที · สไลด์ 12 & สไลด์ 7)

อีกวิธีหนึ่งจากสไลด์ 12 (*Handoffs: Pass the chat on*) และสไลด์ 14 (*Handoff or subagent?*) คือให้บทบาทถัดไปรับงานต่อใน **แชตเดิม** โดยให้ **ผู้ใช้ตรวจงานก่อนเริ่มขั้นถัดไป**:

- ในไฟล์ `.github/agents/ba-analyst.agent.md`, `dev-builder.agent.md` และ `qa-inspector.agent.md` เราใส่บล็อก `handoffs:` พร้อม `send: false` ไว้ให้แล้ว:
  ```yaml
  handoffs:
    - label: "Hand off to Dev Builder (ส่ง Spec ให้ Dev แก้โค้ด)"
      agent: dev-builder
      prompt: "จาก BA Change Request Specification ที่เพิ่งเขียนเสร็จ ช่วยใช้ Skill ui-implementer แก้ไขโค้ดใน ui/preview.html..."
      send: false
  ```

**เลือกทดสอบตาม Session Target (Harness) ที่คุณใช้อยู่:**

> **ถ้า Copilot เตือน `Attribute 'handoffs' is not supported in custom GitHub Copilot agent files.`:** คำเตือนถูกต้อง เราเก็บบล็อกนี้ไว้สาธิต **Local เท่านั้น** ไม่ได้ทำให้ Copilot มีปุ่ม Handoff และไม่ควรเปลี่ยน `target` เพื่อซ่อนคำเตือน ใน Copilot ให้ใช้วิธีที่ 2 ด้านล่างแทน
>
> ไฟล์ฝึกนี้ตั้งใจแสดงทั้ง `skills:` (**Copilot-only**) และ `handoffs:` (**Local-only**) จึงไม่ใช่ไฟล์ตัวอย่างที่ปลอดคำเตือนทั้งสอง Harness สำหรับงานจริงที่ต้องการผ่าน Schema โดยไม่มีคำเตือน ให้เลือก Harness เป้าหมายและตัดฟิลด์ที่ไม่รองรับออก; Body ยังมีลิงก์ Skill และข้อเสนอขั้นถัดไปให้ใช้

### วิธีที่ 1 · หากคุณใช้ **Local harness** (มีปุ่ม Handoff ปรากฏท้ายคำตอบตามสไลด์ 12)
1. เมื่อ `ba-analyst`, `dev-builder` หรือ `qa-inspector` ตอบจบ จะเห็นปุ่ม Handoff ด้านล่างคำตอบ เช่น **`Hand off to Dev Builder`** หรือ **`Hand off to Release Auditor`**
2. คลิกที่ปุ่มนั้น สังเกตว่า:
   - ช่องเลือก Agent สลับไปยัง Agent ปลายทางให้อัตโนมัติ
   - ข้อความจาก `prompt:` ถูกเติมลงในช่องพิมพ์ **แต่ยังไม่ถูกส่งออกไปทันที** เพราะตั้ง `send: false` ไว้ เพื่อให้คุณตรวจหรือแก้คำสั่งก่อนกด Send!
3. กด **Send** เพื่อให้ Agent บทบาทถัดไปรับช่วงต่อในแชตเดิม

### วิธีที่ 2 · หากคุณใช้ **Copilot harness** (สลับ Agent กลางแชตตามสไลด์ 7 จังหวะ 5–6)
*(ตามที่เรียนในสไลด์ 12 ปุ่ม `handoffs:` รองรับเฉพาะใน Local harness ส่วนใน Copilot harness เราสามารถสลับ Agent กลางแชตได้โดยตรงตามสไลด์ 7!)*
1. ในแชตเดิมที่คุณเพิ่งให้ Role Agent ทำงานเสร็จ **ไม่ต้องกด New Chat**
2. Agent มีคำสั่งใน Body ให้เสนอชื่อผู้รับช่วงต่อพร้อมร่างคำขอ **ข้อความนี้ไม่ใช่ปุ่ม Handoff และยังไม่เปลี่ยน Agent / เครื่องมือ** ตรวจผลงานก่อน แล้วคลิก **Agent dropdown** เลือกบทบาทถัดไปด้วยตัวเอง ตรวจร่างคำขอแล้วกด Send หากไม่มีข้อเสนอให้ใช้คำขอตัวอย่างต่อไปนี้:
   - ถ้าคุณเป็น **BA (`ba-analyst`)** → สลับเป็น **`dev-builder`** แล้วพิมพ์:
     ```text
     จาก Spec ข้างต้น ช่วยใช้ Skill ui-implementer แก้ไขโค้ดใน #ui/preview.html ให้ตรงตามข้อกำหนดทั้งหมด
     ```
   - ถ้าคุณเป็น **Dev (`dev-builder`)** → สลับเป็น **`qa-inspector`** แล้วพิมพ์:
     ```text
     จากโค้ดใน #ui/preview.html ที่เพิ่งแก้ไขข้างต้น ช่วยใช้ Skill test-matrix-designer สร้างตาราง Test Cases ตรวจสอบการแก้ไขนี้ลงใน outputs/qa/
     ```
   - ถ้าคุณเป็น **QA (`qa-inspector`)** → สลับเป็น **`release-auditor`** แล้วพิมพ์:
     ```text
     ช่วยตรวจตาราง Test Cases ข้างต้นเทียบกับ #docs/policies/finance-and-sla-policy.md อีกครั้งว่าตกหล่นข้อไหนไหม
     ```
3. **สังเกตตามสไลด์ 7 (จังหวะ 5–6):** ประวัติการคุยก่อนหน้า (**History**) ยังอยู่ครบในแชตเดิม แต่ตั้งแต่คำขอนี้เป็นต้นไป **Body** และ **`tools:`** ได้เปลี่ยนเป็นของ Agent ตัวใหม่ทันที!

**จุดเปรียบเทียบสำคัญ:** ดูตอนสลับจากผู้สร้างที่มี `edit` ไป `release-auditor` ซึ่งระบุแค่ `read`, `search` แล้วตรวจรายการเครื่องมือของคำขอใหม่ นี่คือการเปลี่ยนโปรไฟล์ ไม่ใช่แค่เปลี่ยน Checklist; หากได้ตารางตรวจเหมือนการเรียก Skill เดิมก็ไม่ผิด เพราะวิธีตรวจยังอยู่ใน Skill
